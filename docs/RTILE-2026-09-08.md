# RTILE=64 (paired token tiles) — SUPERSEDED, see FINDINGS-LOG F25/F33

> **2026-09-09: the headline below is WRONG.** RTILE=64 is slower in five
> independent measurements across two boxes, two harnesses and two artifacts
> (exo M4 0.95x, local M4 0.87x, local M3 0.91x, chunk sweep 0.93-0.97x,
> matched-harness 35B-3.4 uniform d4-K2048 0.75x). The 1.23x recorded here has
> never reproduced. The "topology flips the sign" conclusion is void, and so is
> the "geometry flips the sign" replacement briefly logged as F25. Shipped
> default (32) was always correct; only the reasoning was wrong. Text retained
> as a record of the error.

# (original) RTILE=64: a 1.23x on one box, a 0.82x on the ring

The swarm's top lead, and its own refuter's pick over OTILE. Phase 1 decodes
the [32 out-rows x G=64] weight tile once per (out-tile, group) and that
result is identical for every token tile — so codes (WPR*4 B/row), scales
(NGRP*2 B/row) and the CB_DEV codebook loads are re-read once per 32-row
token tile. Pairing two tiles halves exactly that; x bytes and MAC counts
are invariant.

Predicted +5-8%. What we got depends entirely on TOPOLOGY.

## The controlled result

Flash-2.1, the SAME artifact with the SAME module shapes, 9k prefill,
5 reps, min reported:

| placement | RTILE=32 | RTILE=64 | ratio |
|---|---|---|---|
| single-box M3 | 598 tok/s | **736 tok/s** | **1.23x** |
| 2-node ring | **801 tok/s** | 656 tok/s | **0.82x** |

397B-2.2, 2-node ring: 338 -> 289 tok/s = 0.855x, consistent with the ring
column.

**Holding shape constant and varying only placement flips the sign.** The
first pass compared Flash-2.1 single-box against the 397B 2-node and looked
like a shape effect (in=2560/640 vs in=4096/1024, NGRP 40 vs 64); that was a
confound in the experiment, not a property of the kernel. Copying Flash-2.1
to the M4 and re-running it 2-node is what settled it.

### The ring numbers are weaker than they look (Noah, 2026-09-08)

Two things I did NOT control, both of which move a 2-node result:

1. **Node placement is not deterministic.** Which rank lands on which box
   varies run to run — the failing box in the morning's OOM moved between
   M3 and M4 for exactly this reason. `EXO_TENSOR_PREFER_MASTER_RANK0` pins
   only the tensor case, not pipeline. The M3 is 819 GB/s and the M4 is
   546 GB/s, so a swapped assignment changes which box gates the pipeline.
   The last run logged M4=rank0 / M3=rank1; the RTILE=64 run's assignment
   was not captured and cannot be recovered.
2. **Transport is not fixed.** The ring exposes both RDMA
   (`rdma_en3`/`rdma_en4`) and a TCP multiaddr; TCP carries overhead RDMA
   does not. Nothing in these runs recorded which was used.

Consequence: **the single-box 1.23x is clean** — one box, no interconnect,
deterministic. **The ring 0.82x is directionally corroborated but its
MAGNITUDE is not trustworthy**: two different models (Flash-2.1 and
397B-2.2) regressed under RTILE=64 across independent placements, which is
hard to explain by placement noise alone, but the specific ratio could
absorb a rank swap or a transport difference.

To make a ring number trustworthy it must record rank->box assignment and
transport per run, and ideally interleave arms within one placement.

MECHANISM UNMEASURED. RTILE=64 raises the threadgroup allocation from 12288
to 20480 B, which plausibly halves threadgroups-per-core; on one box there is
enough independent work to hide that, on the pipelined ring there may not be.
That is a hypothesis. Do not repeat it as the cause without measuring
occupancy directly.

## Second finding, unrelated but worth having

Flash-2.1 prefills FASTER on the 2-node ring than on one box: 801 vs 598
tok/s at RTILE=32. Two GPUs beat one even paying pipeline overhead, at least
at this size. Nothing in the repo said so.

## Shipped state

`VQ_MOE_GEMMSEG_RTILE`, default **32**. Default stays 32 because the models
that matter most (397B, GLM, Flash-5.5) only run 2-node, where 64 is a
regression. Set `VQ_MOE_GEMMSEG_RTILE=64` for a single-box deployment and
take the 1.23x.

CB_DEV only by budget: beside a 16 KB threadgroup codebook the allocation
would be 36864 > 32768, so the host silently falls back to 32 when the
codebook is resident — arming the flag can never cause an E134 load failure.

Gated by `test_gemmseg_rtile64_numeric` at d4-K8192, d8-K16384 and
d8-IN=640 (pairing and the ragged tail compose), rel<1e-3, which also
doubles as a load gate for the 20480 B allocation. 23/23 pass.

## What this changes about the remaining leads

OTILE 32->64 raises the same allocation the same way, so it is likely to
carry the same topology sign-flip. Its refuter already demoted it on
independent grounds (the x re-read term merely TIES the codebook term on
CB_DEV, so halving it leaves the other dominant). Both facts point the same
way: measure OTILE per topology from the start, and expect the ring to
dislike it.

More generally: every kernel result in this repo from here on should say
which topology it was measured on. Two of today's four measurements would
have been reported wrong without that.

## The sign flips on GEOMETRY too, not just topology (2026-09-08, later)

This document concluded "holding shape constant and varying only placement
flips the sign." True, and incomplete: holding PLACEMENT constant and varying
shape flips it as well.

35B-3.4 (pure d4-K2048, 120 modules), M3 single box, 9k prefill, 3 interleaved
reps, run outside exo through the artifact's own bundled model.py:

| RTILE | reps (tok/s) | min | spread |
|---|---|---|---|
| 32 | 1834.2 / 1837.7 / 1843.4 | **1834** | 0.5% |
| 64 | 1378.5 / 1390.6 / 1395.8 | **1379** | 1.2% |

**0.75x — RTILE=64 is 32% SLOWER**, on the same box where Flash-2.1 measured
**1.23x faster**. Non-overlapping, and the spreads are tighter than any ring
measurement in this file.

    Flash-2.1  d8-K16384  single box   1.23x
    35B-3.4    d4-K2048   single box   0.75x

### Why this was never seen before

`rtile = 64 if (_GEMMSEG_RTILE == 64 and cb_dev) else 32` — RTILE=64 requires
the CB_DEV budget and silently falls back otherwise. Flash-2.1 is d8-K16384,
cb 262 KB, so cb_dev is FORCED by the budget clause and 64 was genuinely
active. d4-K2048 is 16 KB, fits threadgroup, so cb_dev was FALSE and
`VQ_MOE_GEMMSEG_RTILE=64` silently did nothing on it.

**RTILE=64 was structurally unreachable on every d4-K2048 module until the
CB_DEV arm change landed this afternoon**, which flipped ~447 of them to the
device arm and made the flag live for the first time. The first measurement
taken after it became reachable says it is a 32% regression there.

### Consequence

The ring default of RTILE=32 is correct, but this file's reasoning for it was
wrong — it is not only a topology effect. Any future "turn RTILE=64 on for
single-box" change must be gated per GEOMETRY, not per placement, and d4-K2048
is the geometry most of the fleet runs (~447 modules across 397B-3.1,
Flash-3.2, 35B-3.4, 35B-4.6).

MECHANISM UNMEASURED. NGRP is the obvious candidate — Flash-2.1's in=2560
gives NGRP=40 against 35B-3.4's in=2048 (NGRP=32) and in=512 (NGRP=8), and
RTILE=64's whole thesis is amortising phase-1 decode across more token rows,
which pays less when there are fewer groups to amortise over. Do not repeat
that as the cause without measuring it.
