# State — 2026-09-07 (end of the fused-GEMM arc)

Fused segmented VQ-GEMM (`vq_gemmseg2`) — dequant inside the matmul tile,
no fp16 weight materialization, one dispatch per linear over per-tile
(expert, row_start, nrows) metadata on count-sorted rows, Marlin-style
decode-once-per-group into threadgroup, phase 3 as simdgroup_half8x8
with fp32 C tiles resident across the group loop.

## The 397B-2.2 warmup OOM is NOT the kernel — proven

New 107 GB artifact, 3 geometries (151x d8-K16384 legacy, 20x d4-K256
unpacked fused, 9x d4-K2048 fused). Symptom: runner aborts in warmup
prefill with `[METAL] Command buffer execution failed: Insufficient
Memory`. Loads fine (17 s, 2-node pipeline, "Group size: 2, rank 1").

DISCRIMINATING TEST RUN 2026-09-07 15:13: fused path force-disabled on
BOTH nodes -> **identical OOM at 15:17**. The kernel is exonerated.

Dead ends recorded so they are not re-run:
- free-memory pressure: both boxes were ~20% used (exo dashboard); macOS
  reports reclaimable cache as non-free, so vm_stat "free" never binds.
- "model requires 146552 MB" in runner stdout: STALE, last written
  10:05 (Flash's line, not the 397B's).
- missing eval fence in the fused path: plausible story, NOT the cause;
  the fence was added and then REVERTED (it cost 5.7->6.6 s, 1.65x ->
  1.42x, and fixed nothing measurable). Repo now matches published
  artifacts exactly — no republish needed.
