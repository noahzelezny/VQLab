## The kernels

`_SRC_DENSE_D2_TILED` / `_SRC_DENSE_PACKED_D2_TILED` stage one block span of x
instead of the whole row, so the threadgroup budget loses its layer-width
term. `_SRC_DENSE_D4_TILED` / `_SRC_DENSE_PACKED_D4_TILED` keep a 64 KB
codebook in device memory and tile x, which is the only way d=4 fuses at all.
Bit-identical to the kernels they replace wherever both can run, and MORE
accurate than the decode fallback they displace (2.64e-4 vs 4.05e-4 max
relative error against an exact float64 reconstruction).

Expert-kernel work (E141, peer session, commit 108fe9e) is simdgroup-per-row,
gated `NGRP >= 32` AND `N <= 20` pairs. It does not change the 397B's
seq2/seq1 ratio.

## Gates now in place

- `vqlab smoke --strict` (default on) fails when the runtime resolves from
  anywhere a downloader would not have it, checks each family's own kernel
  route, and treats a VQ-patched mlx-lm as a failure in itself.
- `vqlab check-release` statically rejects `from|import mlx_lm.models.vq_*` in
  a bundle (no model load, would have caught the incident at build time) and
  runs the strict smoke.
- `vqlab publish` runs the gate before upload, with no override, and re-hashes
  every file before and after to catch a concurrent edit.

## The methodological note worth keeping

Every false alarm today came from generalising a single sample: one venv, one
dict entry, one machine, one memory counter. The OOM scare, "exo never runs
the bundle", the shadowing claim, "Flash-Next has a small codebook", "1.45x
faster than stock" -- all the same error, and all corrected by measurement.
The findings that held up were the ones checked before they were reported.
Establish that an environment is the one that runs before describing what it
does; `ps aux` beats reading a plausible directory.
